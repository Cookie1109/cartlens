# Audit log

`GET /api/v1/streams/{streamId}/audit/{algorithm}?sessionId=...&windowId=...`

For continuous streams, omit `windowId` to read the latest completed audit atomically: `GET /api/v1/streams/{streamId}/audit/{algorithm}?sessionId=...`. The same schema is returned, including the actual `windowId` and its own configuration. The session and algorithm checks remain enforced. This avoids a stale-window 404 when mining advances between a `/live` read and the audit request. Supplying `windowId` preserves the original strict matching behavior. Only one immutable snapshot is read; this never re-runs mining.

For compatibility with backends that still require `windowId`, the browser sends `windowId=<live hint>&latest=true`. New backends treat `latest=true` as an explicit latest-snapshot read and ignore the window hint. Older backends ignore the unknown `latest` parameter and use their existing strict-window read. This prevents a missing-parameter 500 during an upgrade without issuing a speculative failing request. On an older backend, an already-retired hint can still return 404; continuous atomic reads require the newer backend. `latest` defaults to false, preserving strict callers.

`algorithm` is `FWUDS_CT` or `FWUDS_DWT`; `sessionId` is the live snapshot's session ID (not the secondary algorithm's run ID). The response is an immutable audit of that algorithm's latest completed window. A mismatched session/window, missing window or ORACLE returns 404 `RESULT_NOT_FOUND`. Unknown enum values return 400. The endpoint reads the captured trace; it does not run mining to reconstruct historical traces. Loading an evicted stream still uses the existing stream-recovery mechanism.

Response: `algorithm`, `windowId`, `config`, `sumTwu`, `previousSumTwu`, `incomingTwu`, `expiredTwu`, `currentLcTid`, `initialWindow`, `evaluatedCandidates`, `acceptedCandidates`, `prunedCandidates`, `patternCount`, `sampleLimit`, `omittedCandidates`, and `samples`. When `initialWindow=true`, the session is building its first window (including after recovery); `previousSumTwu` covers the already accumulated panes, not a previous complete window. This flag remains true even when recovery adjusts the public window ID.

Each sample contains `operation`, `items`, `itemsTruncated`, `numerator`, `wus`, `accepted`, nullable `support`, `leftSize`, `rightSize`, `outputSize`, `evidence` and nullable `pruningBound`. CT evidence contains up to eight circular TIDs; DWT evidence contains up to eight `(pre, post, weight)` codes. Early DWT pruning exposes its conservative weight bound; its numerator and WUS are null because the full intersection was not computed. A rejected singleton has no materialized WUNList. All WUS decisions use DECIMAL128 before display rounding.

Up to 48 candidate samples are kept per algorithm per window, with at most 16 singletons so joins always have room. Each sample contains at most 24 item labels (long names keep their first 96 characters plus an ellipsis). Counts cover every evaluated candidate; omitted samples do not truncate mining results. Only the latest pair of audits is retained in memory. Audit is excluded from `/live`. The client fetches only while the modal is open and visible. Window hints from the existing live feed are coalesced: at most one audit request starts per second, with one request in flight and no per-window queue. It reads the latest endpoint, labels every view using the returned window/configuration, and suppresses old rows immediately when a newer live window is known. A slow response is discarded if already superseded, then the latest window is requested within the rate limit. Closing/scope changes abort the request; hidden tabs suspend new audit requests and resume from the latest window. Retry uses the same rate limit. There is no independent polling interval or historical cache. Filter, search text, selected log page and relative pane page survive window changes; expanded sample/transaction rows and explanations do not. Audit history is not persisted.

The “Log khai phá” and “Dữ liệu cửa sổ” views render separately as accessible tabs (arrow/Home/End keyboard navigation). A shared, non-interactive window summary above the tabs shows the window number, transaction range and panes once; the modal title contains only the algorithm. Only the tabs change views. Mining thresholds, candidate counters, example filters/search and calculation explanations belong to the mining tab. Transaction rows, item search and a single pane-pagination bar belong to the data tab, without a repeated window heading or mining controls. Choosing the data tab loads source transactions through the existing `GET /api/v1/streams/{streamId}/transactions?after=...&limit=...` endpoint. For window `w`, pane size `p`, pane count `k`, the ordinal range is `(w-1)*p+1` through `(w+k-1)*p`. Each data page contains exactly one pane: page index `j` in `[0,k)` selects pane `w+j` and ordinal positions `(w+j-1)*p+1` through `(w+j)*p`. The pane list scrolls only when `p>5`. To keep large panes bounded, a virtual viewport fetches at most 20 rows at a time: `after=(w+j-1)*p+chunkStart`, `limit=min(20,p-chunkStart)`. Only one block is retained/mounted; small scroll movements inside it do not refetch. Scrolling or keyboard navigation can reach the last transaction of the pane without including a neighboring pane. The panel never includes the following partial pane. Each transaction shows its original ID, source pane, item preview and TWU; expanding it shows quantities and weights, in a separate contextual popover, with at most 10 item rows rendered at once. Data is fetched only while the data tab is selected, with cancellation on close, page change or window change. The selected view, relative transaction page, page-jump input and its keyboard focus survive a sliding-window update; transaction rows and expanded transaction reset to the new window. Page navigation is clamped to the window size. Users can jump directly to any pane page; item search is local to the expanded transaction. Candidate search covers only the at-most-48 captured examples, never the full mining result. While the audit modal is open, the background full-tree/CTset and pattern-list components are unmounted so they do not repeatedly fetch and render large results behind it. No mining or new backend endpoint is required.

The audit modal and log list have no scrollbars. The mining list paginates at most five rows (fewer on short screens); its search and status filters sit directly under “Ví dụ tính toán”. Long method/sample explanations open in contextual popovers, preserving the frame and visible controls. Only transaction panes with more than five rows have a scrolling list. Changing a pane/window or closing the view aborts its pending block request and drops that block.
